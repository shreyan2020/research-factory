# Workshops and live delivery

## Design the activity before the polling mechanism

Start with the capability participants should practice. Build realistic decisions that expose a misunderstanding or tradeoff, using the evidence participants would actually see. Avoid a quiz whose answer is obvious from wording unless simple recall is the intended objective.

Use this activity pattern when it fits:

1. **Scenario:** A specific incident, artifact, or decision with only the facts needed to reason about it.
2. **Question:** A clear response task. Do not reveal the answer or cue the preferred option before discussion.
3. **Discussion:** Time to compare reasoning, including a prompt for contrasting answers.
4. **Debrief:** Explain what matters, why plausible alternatives fail or remain defensible, and what participants could do next.

Each activity's presenter notes should contain its learning purpose, anticipated responses, discussion probe, debrief, approximate duration, and a simple fallback. Include these only where they help facilitation; do not repeat a large template on every slide.

Mark synthetic cases where confusion with real data would affect interpretation. Do not invent participant outcomes, institutional policy, study permissions, payment rules, or platform capabilities. Verify changing policy or service details against an authoritative current source.

## Budget real classroom time

Use the actual available teaching time, including transitions, discussion, questions, breaks, and setup. A booking window is not necessarily continuous instruction. If institutional scheduling matters, verify it rather than assuming it.

Give optional activities a clear removal order so the presenter can finish coherently. Do not label required content optional merely to force an unrealistic schedule. Keep the main path understandable if optional material is skipped.

Separate participant material from facilitator support. Participant slides should make the decision and necessary evidence clear. Notes or a requested facilitator pack should handle timing, likely misconceptions, further explanation, and recovery steps.

## Test a live integration before scaling it

For polls, embedded slides, authentication, media, or external links, verify one representative end-to-end path on the intended surface early: presenter opens content → participant can access or respond → presenter returns to the correct next slide. A configured session or saved restart index does not establish that this path works.

Maintain a compact mapping between activities and slide ranges when an integration needs it. Recheck the mapping after slide additions or deletions. Test the meaningful interaction, not every identical poll redundantly.

If the same failure repeats without new evidence, stop duplicating configuration work. Diagnose the smallest failing step. Authentication loops, inaccessible browser settings, and blocked embeds may be outside the deck's control. Do not bypass access controls or describe a login failure as a slide-rendering defect.

## Recover without losing the learning objective

When an integration is blocked, preserve completed content and explain the concrete limitation. If the user has allowed a simpler delivery, convert the same activity into show-of-hands, pairs, written reflection, or open discussion. Retain the scenario, reasoning task, and debrief. Remove obsolete joining cues, QR codes, polling instructions, and notes so the delivered copy is internally consistent.

Preserve the user's selected output destination and editable artifact when falling back. Do not silently switch a requested native file into a different product, or claim an export exists because a viewer offers export. If the fallback changes an explicit requirement, obtain that missing decision while completing independent work.

Keep earlier configurations intact unless the user asked to delete them. Make the current classroom copy identifiable so the presenter does not open the abandoned integration version by mistake.
