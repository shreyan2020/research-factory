# Story and evidence

## Research talks and results decks

Begin with the substantive problem and what the audience needs to understand or decide. The paper's section order is not automatically the talk's order. Select the evidence that supports the talk's central contribution and keep necessary qualifications adjacent to the finding.

A useful sequence is problem → concrete example → approach → evidence → implication, but preserve a user-specified structure and change this sequence when the material warrants it. A background or method slide can use a plain subject title. Use a finding as its title only when the slide establishes that finding.

For each substantive slide, be able to answer:

| Working field | What to retain |
| --- | --- |
| Purpose | What this slide enables the audience to understand or do |
| Visible content | The smallest complete explanation, example, chart, table, or question |
| Claim status | Observed result, source-reported statement, interpretation, proposal, or illustrative scenario |
| Evidence | Exact source, passage/table/figure or run output, relevant version and denominator |
| Notes | Explanation the presenter needs but the audience does not need to read |
| Transition | Why the next slide follows |

Use this as a working model, not a requirement to add every field to every slide. Preserve a source ledger already supplied by the paper or analysis workflow instead of duplicating it.

## Match the visual to the evidence

- Use a comparison table when readers need to inspect differences across the same dimensions. Align definitions, periods, units, and denominators before placing values side by side.
- Use an evidence chain when a result depends on source passage → extraction/coding → interpretation. The audience should be able to tell which steps were automated and which were reviewed.
- Use separate views or an explicit version note when source changes, analytical changes, and presentational changes could be confused. A new report year is different from rerunning a model or restyling a chart.
- Keep charts, tables, and requested editable diagrams editable using the chosen format's supported objects. Screenshots are appropriate when the screenshot itself is evidence; do not flatten data objects merely for appearance.
- Use restrained citations in notes or alongside the relevant claim as the format and audience require. Never hide a qualification that changes the audience's conclusion in notes alone.

For empirical comparisons, retain sample sizes, the actual evaluation unit, metric direction, baselines, exposure state, and the scope of uncertainty. Do not describe agreement with reference labels as scientific truth, a software test as a user evaluation, or a proposal as a validated mechanism.

## Literature synthesis

Organize literature around the problem each source helps explain. Make a comparison useful by identifying the substantive distinction: objective, data, method, evidence, or limitation. Do not produce a procession of paper summaries without a question tying them together.

Use primary sources for substantive claims. Verify bibliographic details and the supporting passage when citing a source. A source recommended in a previous chat is a lead, not a verified citation for the new deck. Do not claim that a display improves comprehension or review speed unless an appropriate evaluation supports it.

## Revision discipline

Before editing, inspect the current artifact and the user's latest requested changes. For a limited revision, maintain a short internal list of affected slides and propagate consequential changes to references, notes, captions, and numbering. A content source is not automatically a design template.

When shortening, remove duplicate explanations and weak examples before removing essential methods or qualifiers. Move detailed backup material to an appendix only if the user permits it and the presentation remains understandable. Avoid shrinking all text to meet an arbitrary density target.
