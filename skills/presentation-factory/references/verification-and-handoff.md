# Verification and handoff

Verify the thing the user will use. A successful build, valid package, attractive preview, and working presentation session establish different facts.

| Check | What it establishes | What it does not establish |
| --- | --- | --- |
| Source and content review | Required material is covered and claims agree with inspected evidence | Good rendering or functioning links |
| Package/import checks | Saved structure is readable by the tested importer and passes checked constraints | Scientific accuracy, successful native application use, or interaction behavior |
| Rendered slide inspection | Actual visible text, layout, charts, contrast, and cropping can be inspected | Native editability or a different application's rendering |
| Object inspection | Required editable objects and notes exist in the saved artifact | Presenter or audience usability |
| Target-surface check | The inspected delivery flow works in that surface at that time | Other browsers, accounts, future availability, or untested interactions |

## Content review

Check the requested slide count, order, required material, and latest user edits. Read titles and body text together. Remove conclusions stronger than the evidence, duplicate headings, decorative labels, and generic claims. Preserve enough explanation for novices to understand important terms.

Check numerical comparisons against their source values, units, populations, time windows, and denominators. If calculations are present, verify the actual arithmetic and the interpretation. Empty, skipped, or inapplicable checks are not positive evidence.

For workshop revisions, review notes and companion material as well as visible slides. A removed polling tool can remain accidentally embedded in presenter cues or participant instructions.

## Visual and delivery review

When using a new import/export route, test a representative file through the actual finalization and target-rendering path before editing the whole deck. A successful initial import does not establish that later validation subprocesses or final file creation have their required runtime configuration and access. Use current bundled documentation for those mechanics; do not turn one environment failure into a permanent tool ban.

Render the final saved version, not an earlier draft. Inspect every slide at a useful scale, spending extra attention on dense evidence, diagrams, tables, and changed content. Correct overflow, unreadable labels, clipping, missing images, accidental answer disclosure, and inconsistent source text. Use the supplied design before generic style suggestions.

If a render appears to drop or alter a character, inspect the saved text/object and repeat the affected export before rewriting correct content. Distinguish a content defect, a layout defect and a transient renderer failure. Keep the final inspected render tied to the exact delivered file.

Apply the active format skill's required validation and finalization. Recheck affected slides after a correction and any dependent numbering or navigation; do not run a redundant test suite merely to add checks. If a platform blocks preview, state which review could not be done and continue with available checks without calling them equivalent.

When the task includes a live interaction or native application requirement, inspect that actual path when tools and access permit. A browser screenshot of a file list is not evidence of opening the deck. Say "checked in PowerPoint" only after opening and inspecting it there.

## Handoff contract

Deliver only the requested final artifacts using the format skill's supported delivery mechanism. Keep build scripts, scratch slide maps, test outputs, and QA logs out of the final response unless requested. Companion handouts or facilitator packs are separate deliverables only when requested or already part of the agreed scope.

Internally distinguish:

- the authoritative source and revision;
- the saved final deck and its destination;
- any separately exported file;
- whether an embedded or native presentation flow was actually tested;
- unresolved issues that affect the presenter or audience.

If the final deck is in a viewer with download capability, state that precisely. Do not call a downloadable viewer link a completed local file export. If an explicit file export cannot be completed, identify that remaining deliverable rather than treating the task as fully finished.

Keep the user-facing handoff short: the deck, requested supporting material, and any limitation they need to act on. Do not fill it with self-ratings or a recap of routine verification.
